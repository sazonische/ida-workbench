# IDA Workbench — карта проекта

Ориентировочный документ для работы в этом репозитории: что где лежит, как связано и какие
инварианты нельзя ломать. Читается сверху вниз; разделы независимы.

Нативный C++/Qt 6 менеджер инстансов [`ida-pro-mcp`](https://github.com/mrexodia/ida-pro-mcp).
Держит список бинарников по тегам, создаёт для них IDA-базы и поднимает по MCP-серверу на
отдельном порту для каждой пары `(tag, module)`. Версия берётся из `project(VERSION)` в
[CMakeLists.txt](CMakeLists.txt) (сейчас 1.3.0) → `src/version.h.in` → `version.h` в build-каталоге.

## Сборка и тесты

```powershell
build.cmd          # динамический Qt → dist/
build-static.cmd   # статический Qt (vcpkg) → dist-static/
ctest --test-dir build --output-on-failure
```

Ожидается Qt 6.8.3 (`C:\Qt\6.8.3\msvc2022_64`), Visual Studio с CMake/Ninja. Тесты запускать
**через ctest**: CMake сам подкладывает Qt в `PATH` (`ENVIRONMENT_MODIFICATION`), напрямую
`manager-config-tests.exe` упадёт с exit 53 (нет Qt6Core.dll) или без argv — с
`FAIL: fake helper paths supplied` (нужны пути к `fake-depot` и `fake-analyzer`).

- `AUTOMOC ON`, **`AUTOUIC OFF`** — намеренно: иначе `ui_util.h` был бы принят за вывод `uic`.
- Ресурсы вкомпилированы: QSS, шрифты (Roboto Flex, Roboto Mono, Material Symbols), иконки,
  а также три python-скрипта под префиксом `/scripts`.
- `WIN32_EXECUTABLE ON` — консоли нет, всё в лог-панель и файл лога.

CI — [.github/workflows/windows.yml](.github/workflows/windows.yml). Одна сборка, один артефакт:
статический одиночный exe. Qt компилируется vcpkg из исходников, поэтому холодный кэш пакетов
стоит часы, а тёплый — минуты; шаг упаковки проверяет через `dumpbin`, что exe не импортирует
Qt/MSVC-DLL. Артефакт **не кладёт python-скрипты рядом с exe** — это переключило бы `_scriptDir`
на каталог загрузки, где `ensureHelperScripts` их не обновляет (в локальных `dist/` копии
остаются намеренно: правишь скрипт рядом с exe без пересборки). Версия (джоба `meta`): **на теге версию задаёт тег** (`v` отбрасывается), вне тега —
`project(VERSION)`. Тег прокидывается в сборку как `-DIDA_WORKBENCH_VERSION`, которую
[CMakeLists.txt](CMakeLists.txt) объявляет CACHE-переменной со значением `${PROJECT_VERSION}` по
умолчанию, а [src/version.h.in](src/version.h.in) подставляет в `APP_VERSION`. Смысл: exe в
релизе всегда называет ту версию, под которой его скачивают, и выпуск не зависит от того, вспомнил
ли кто-то поправить файл. ⚠️ Значение `-D` обязано быть **в кавычках целиком**
(`"-DIDA_WORKBENCH_VERSION=1.2.3"`): без них PowerShell рвёт токен и в exe уезжает версия `1`.

Два входа в релиз, оба без ручной загрузки файла:

- **тег** (push тега или Draft a new release в UI, который тег создаёт) → сборка с версией тега,
  ассет прикладывается; если релиза ещё нет — создаётся;
- **бамп** `project(VERSION)` + push в `main` → тег и релиз создаёт сам `gh release create`
  (`--target $GITHUB_SHA`).

Публикация идемпотентна и **не краснеет на пустом месте**: версия, уже помеченная тегом на другом
коммите, — это состояние любого обычного push'а после релиза, поэтому джоба просто пишет
«nothing to release» и выходит с нулём. Релиз, существующий **без ассетов** (создан руками),
доливается недостающими файлами; уже приложенные никогда не перезаписываются. Теги, созданные `GITHUB_TOKEN`, не запускают
workflow повторно — рекурсии нет.

Набор фич `qtbase` **прибит явно** (`core` = без дефолтных) и в CI, и в комментарии
[build-static.cmd](build-static.cmd): дефолтные фичи порта добавляют icu, openssl, jpeg, zstd,
brotli, sql (+postgresql через `sql-psql`), dbus, opengl, testlib — часы лишних сборок портов, а
статическая icu раздувает exe с 22 МБ до 58 МБ. Приложение линкует только Widgets и Network, а
HTTPS (загрузка `steam.inf` с GameTracking) работает без openssl через schannel — в локальной
статической сборке `QT_FEATURE_ssl 1`, `QT_FEATURE_schannel 1`. `--clean-buildtrees-after-build`
обязателен: buildtree qtbase — десятки гигабайт, а диск раннера столько не держит. При падении
джоба собирает `buildtrees/**/*.log` в артефакт `vcpkg-logs` — иначе от многочасового прогона
остаётся только `BUILD_FAILED`.

Кэш архивов vcpkg разделён на `cache/restore` + `cache/save` с `if: always()`: сохранять надо
сразу после дорогого шага, иначе упавший тест выбрасывает часы сборки qtbase и следующий прогон
начинает с нуля. Ключ включает ревизию vcpkg (образ раннера обновляет её раз в несколько недель)
и хеш файла триплета, `restore-keys` позволяет устаревшему кэшу хотя бы подсеять пересборку.

Отличия CI от локальных `.cmd`: генератор — Visual Studio (без `-G`, чтобы не привязываться к
версии VS на раннере) вместо Ninja, поэтому бинарники лежат в `build-static/Release/`, а `ctest`
требует `-C Release`. Статический триплет vcpkg переопределён в [.github/vcpkg-triplets/x64-windows-static.cmake](.github/vcpkg-triplets/x64-windows-static.cmake)
(`VCPKG_BUILD_TYPE release` — debug-половина qtbase не пакуется); имя триплета сохранено, чтобы
условие статического CRT в [CMakeLists.txt](CMakeLists.txt) продолжало срабатывать.

## Модель данных

```
config.json → LoadConfig → ConfigView → RebuildInstances → _instances (Instance)
                                                              ↓ Refresh
                                                       LibRow/Cell → таблица UI
```

Пути пользователя: `%USERPROFILE%/.ida-workbench/` — `config.json`, `ui-state.json`, лог.

Два **независимых** типа workspace (см. README для схемы JSON):

- `workspaces` (папочные): копируют относительные пути из `source` в `output`; Replace
  архивирует прежние файлы в `output/revisions/<timestamp>/`.
- `steamWorkspaces`: качают те же относительные пути через DepotDownloader; каждая сборка
  живёт в `dir/<ManifestID>/`, поле `current` указывает на активный манифест.
- `extraLibs`: одиночный бинарник по абсолютному пути со своим тегом.

Порты (единственный источник формулы — [manager.h](src/core/manager.h)):
`AutoScanPort = scanBasePort + fileIndex + tag.portOffset`, `AutoExtraPort = scanBasePort + 1000 + index`,
плюс `portOverrides` — закреплённый порт для конкретной пары `(tag, name)`.

Ключи, которые легко перепутать:

- `Target` = `(tag, name, revision)`; **пустая `revision` = Current**.
- `TargetKey` = `tag\tname\trevision` (и в UI, и в менеджере).
- `RowKey` (только UI) = `name\ttag`.

Валидация (`validateConfig`, вызывается и при загрузке, и при сохранении): непустые host/logDir,
обязательный явный `#RRGGBB` у каждого тега, только относительные пути без `..`, уникальные теги
и имена внутри тега, отсутствие коллизий портов, поддерживаемая пара AppID/OS (730 windows/linux).
`LoadConfig` может дописать нормализованный JSON, если в файле не хватало полей или цветов.

## Потоки и сигналы

`Manager` создаётся в UI-потоке и переносится в `QThread`; всё общение — очередные сигналы.
Кастомные типы зарегистрированы в `main.cpp` — новый тип в сигнале требует `qRegisterMetaType`.

- UI → воркер: `RequestRefresh/OpenIda/Start/Stop/Analyze/StopOperations/Replace/DepotUpdate/SaveConfig/ImportConfig/StoredVersion`.
- воркер → UI: `Log`, `StatusReady`, `ReadinessChanged`, `AnalyzeStarted/Finished`,
  `OperationChanged` (по цели: `analyze` | `ida`), `WorkspaceOperationChanged` (по тегу: `depot`),
  `ConfigLoaded`, `ConfigSaveFinished`.
- Прямые (не через очередь) вызовы: `RequestStopDepot()` — атомарный флаг, работает даже когда
  воркер занят; `StopOperations` в деструкторе окна — `BlockingQueuedConnection`.

⚠️ `UpdateDepot` блокирует воркер на всё время закачки и внутри крутит
`QCoreApplication::processEvents`, поэтому отложенный `Refresh` может выполниться **посреди**
депот-операции. Именно поэтому UI на время депота останавливает авто-Refresh (через `_busy`).

## Операции

| Команда | Что делает и чем защищена |
|---|---|
| `Refresh` | `PollIdaProcesses`, `ReadinessChanged`, параллельный опрос портов (`std::async`, 500 мс), сбор `LibRow` |
| `Start` | detached `cmd /c start "" /min ida.exe -A -S start_mcp.py <db>`, env `IDA_MCP_PORT/HOST/LOG` |
| `Stop` | `PidOnPort` (`GetExtendedTcpTable` / `ss`) → `IsExpectedServerProcess` (сверяет имя exe с `ida.exe`) → **сначала просьба закрыться** (WM_CLOSE видимым окнам / SIGTERM), одно общее окно ожидания `kStopGraceMs` на весь батч → повторная проверка владельца pid → `KillPid` → зачистка распакованной БД. Чужой процесс на порту не убивается: `[refused]` |
| `Analyze` | по процессу `idat` на цель, параллельно; БД отводится в `.ida-workbench.bak` и восстанавливается при провале (`FinalizeAnalyze`); таймаут 2 часа; аргументы = `analysisArgs` без `-B`, плюс `-A -S analyze_ida.py -o<db> <bin>` |
| `Replace` | только папочный workspace и только Current; архив в `revisions/<ts>`; если у источника рядом есть .i64 — переносится вместе с бинарём (анализ не нужен), иначе устаревшая БД удаляется |
| `OpenIda` | `startDetached(ida.exe, [.i64 или бинарь])`, pid в `_idaPids`; `PollIdaProcesses` снимает признак, когда IDA закрыта |
| `UpdateDepot` | `-manifest-only` для GID → фильтр по каталогу манифеста → staging → установка в `<ManifestID>`; sidecar-БД переносится, если SHA бинаря совпал; `current` пишется в конфиг только при реальном изменении |

`UpdateDepot` **не требует остановки серверов workspace** — ни своих, ни чужих. Два режима
установки (`completeInPlace`):

- каталога `<ManifestID>` ещё нет → всё собирается в staging и одним атомарным `rename`
  встаёт на место (тенантов нет, конфликтовать не с чем);
- каталог уже есть (прерванная закачка) → он **дополняется по файлам**, а не подменяется
  целиком. Файл с совпавшим SHA не трогается вовсе (`[depot] … already had … — left
  untouched`) — вместе с его БД и живой сессией; изменившийся файл перезаписывается, но если
  он занят (анализ / открытая IDA / поднятый сервер — `heldBy` по абсолютному пути, как в
  `TargetBusy`), то пропускается с `[skip]`. Именно это позволяет докачать остальные модули,
  пока один отдаётся MCP-сервером. Подмена каталога целиком требовала бы эксклюзивного
  доступа ко всему содержимому — и удаляла бы всё, чего нет в `files`.

Перенос sidecar-БД никогда не валит операцию: ошибка копирования и живая распакованная БД
(`kUnpackedDbExts` рядом с предыдущим бинарём → переносится только упакованный `.i64`) дают
`[warn]`, цена — лишний Analyze. После смены `current` поднятые серверы продолжают отдавать
**прежний** манифест, пока их не перезапустят, — об этом пишется `[warn]` со списком модулей.

`TargetBusy` защищает по **пути бинаря**, а не по ключу: та же база, открытая под другой
ревизией, тоже считается занятой.

Пока база открыта, IDA держит её распакованной в `.id0/.id1/.id2/.nam/.til` и складывает
назад в `.i64` только при штатном закрытии. Поэтому `Stop` сначала просит IDA закрыться сама
(тогда правки MCP-сессии сохраняются, а распаковка исчезает), и лишь потом убивает. После
убийства распакованные части сносятся — но **только если рядом есть упакованный `.i64`**: без
него эти файлы и есть единственная копия работы (прерванный импорт), и их оставляют с
предупреждением. `kUnpackedDbExts` / `kDbExts` — единственный список этих расширений
(`Replace` до сих пор держит свою локальную копию `DB_EXTS`).

Статусы ячейки (`Cell.state`): `Ready`, `Update available` (SHA копии ≠ источник),
`Not analyzed`, `Re-analyze` (.i64 старше бинаря), `No binary`, `—` (инстанса нет).
SHA кэшируется по `size + mtime` (`_shaCache`).

Все команды воркера **устойчивы к смешанным батчам**: каждая цель проверяется отдельно и
непригодная логируется как `[skip] <label>: <причина>` + итоговая сводка.

## Доступность кнопок

Правило: **отмеченные строки — это область действия, а не обещание, что каждая подходит.**
Список файлов в workspace — пожелание; депот может не привезти модуль, в папке-источнике может
не быть бинаря. Поэтому кнопка активна, если действие применимо хотя бы к одной отмеченной
строке, и выполняется ровно по пригодному подмножеству. Пропущенное всегда видно: в тултипе,
в диалоге подтверждения и в логе.

Единственный источник истины — `MainWindow::ActionBlocker(Action, Target)`: возвращает причину
непригодности или пустую строку. На нём построены состояние кнопки, её тултип и батч команды.
`EligibleTargets()` фильтрует выделение и собирает список `имя — причина`.

| Действие | Область | Требует от строки | Глобальные условия (gate) |
|---|---|---|---|
| MCP Start | подмножество | есть .i64 | `_ready` |
| Open IDA | ровно одна строка | есть .i64 или бинарь | `ida.exe` существует |
| Analyze | подмножество | есть локальный или исходный бинарь | `_ready`, не выбрана архивная версия |
| Replace | подмножество | есть бинарь в источнике + папочный workspace | не выбрана архивная версия |
| Depot update | весь workspace | тег — Steam-workspace с включённым депотом (состояние строки не важно) | депот не идёт, не архивная версия, ровно один тег |
| Delete | подмножество | — (только транзиентные конфликты) | депот не идёт, не архивная версия |
| Stop | подмножество | строка занята (up/starting/analyzing/depot) | — |

Причины делятся на **транзиентные** (`MCP server running — stop it first`, `open in IDA`,
`analyzing`, `depot update running`) — их пользователь может снять, и **постоянные**
(`no binary here`, `no binary in the source folder`, `not a Steam workspace`).

Строгими намеренно оставлены: Open IDA (при 5 отмеченных непонятно, какую открывать) и
Depot update (операция уровня workspace — DepotDownloader тянет весь `files`, а не отмеченные
строки). Контекстное меню таблицы зеркалит состояние и тултипы кнопок.

Depot update отвечает **до** транзиентных проверок строки (как и Stop): отмеченная строка для
него — лишь способ назвать workspace, поэтому ни её собственный сервер, ни чужой сервер того же
тега кнопку не гасят. Отказ возможен только на уровне отдельного файла и только после ответа
Steam, поэтому о нём сообщает воркер строкой `[skip]`, а не тултип.

## Блокировка `_busy`

`_busy` — «редактор занят целиком». Пока он выставлен, `UpdateActionButtons()` выходит на первой
строке, а всеми виджетами владеет `OnBusy()`.

**Правило: кто взял `_busy`, обязан гарантировать событие освобождения на каждом пути выхода.**

- Запись конфига (Settings save/import, правка порта в таблице, Add binary, Delete) освобождается
  по `ConfigSaveFinished` — он эмитится на всех выходах `SaveConfig`/`ImportConfig`.
- Depot update освобождается по `WorkspaceOperationChanged(tag, "depot", false)`, потому что
  воркер сохраняет конфиг **только при изменении манифеста**: обновление, ничего не изменившее,
  иначе оставляло UI заблокированным навсегда. Все выходы `UpdateDepot` проходят через
  `finishDepot()`.
- Пока активен депот, кнопка Stop остаётся доступной — иначе отменить DepotDownloader нечем.
- `UpdateActionButtons()` вызывается **в конце** `OnBusy()`, после blanket-присваиваний `!busy`,
  чтобы за ним осталось последнее слово по `Add binary` и `Settings`.

## UI

Шапка (заголовок, чипы готовности, счётчики) → тулбар (6 действий, утилиты, MCP data) →
комбо Workspace/Manifest (только в режиме Tabs) → таблица → лог-панель в `LogSplitter`
(двойной клик по ручке свёртывает панель, высота помнится) → футер.

- Режимы: `_view == 0` — плоский список всех тегов, `_view == 1` — табы по тегу (колонка Tag
  скрыта, работает комбо Manifest/Revision).
- Сортировка своя: `ApplySort()` считает мультиключевой порядок и пишет ранг в скрытую колонку
  `COL_ORDER`, физически двигает строки `sortItems`. Клик по заголовку: off → asc → desc → off;
  индикатор — только тон текста заголовка.
- `_rowState` и `_rowOf` ключуются по `(name, tag)`, а не по индексу строки, — сортировка
  переставляет строки в любой момент.
- Архивная версия выбирается комбо; `ActiveRevision(tag)` подмешивается в каждый `Target`,
  и такие цели read-only (воркер отказывает Analyze/Replace).
- Закрытие окна сворачивает в трей (Exit — только из трея); `ui-state.json` хранит раскладку
  сплиттера.
- Авто-Refresh: 4 с, когда что-то поднято или грузится, иначе 15 с; ручной Refresh крутит иконку.

## Ловушки

1. `setRowHidden` привязан к индексам строк, а не к элементам: после сортировки фильтр по тегу
   надо переприменять (делается в `OnStatus`), иначе скроется не та строка.
2. `Pal::` (C++-рисование) и токены в `theme.cpp` (QSS) — две копии одних цветов.
3. Тег без `#RRGGBB` в конфиге — сохранение будет отклонено валидацией.
4. И GUI, и python-процессы пишут в **один** лог-файл через lock-файл; `Log::EnforceCap`
   вызывается таймером раз в 5 с, потому что писателей несколько. Захват lock-файла
   ограничен `kLockWaitMs` (2 с) и держится под `g_mutex`: умерший или зависший внешний
   держатель не должен морозить наш поток — потерянная строка лога дешевле зависания.
5. Завершение работы обязано быть конечным. `ExitFromTray` зовёт `QCoreApplication::quit()`
   явно (не полагаясь на `quitOnLastWindowClosed` — одно видимое диалоговое окно оставило бы
   процесс без окна, но живым), а деструктор окна ждёт воркер `wait(15000)` и при таймауте
   делает `std::_Exit(0)`. Именно **не** `QThread::terminate()`: воркер может держать
   `g_mutex` лога, и тогда следующая же строка (в том числе от самого Qt при разрушении)
   заблокирует нас насмерть. Зомби-процесс хуже незавершённого teardown: single-instance
   заставит следующий запуск молча «активировать» мертвеца.
6. Приложение одноэкземплярное; второй запуск активирует первое окно и выходит с кодом 0.
   Из-за этого смоук-тест собранного exe при уже запущенном приложении завершается с кодом 0
   мгновенно — это не падение.
7. `.git/` в рабочей копии сейчас нечитаем для git («not a git repository») — сравнить diff
   штатно не получится.

## Стиль кода

Зеркалит стиль плагина cs2-duels:

- Классы без префикса `C` (`MainWindow`, `Manager`, `ChipDelegate`), методы PascalCase,
  поля `_camelCase`, константы `UPPER_SNAKE` или `kCamel` (`kDbExts`, `kStartGraceMs`).
- Файлы snake_case; неймспейсы `Ui`, `Pal`, `Log`.
- Переопределения Qt остаются camelCase (`paintEvent`, `closeEvent`, `sizeHint`).
- Отступы — табы. Комментарии объясняют **почему**, а не что; такой плотности и стоит держаться.
